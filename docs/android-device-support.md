# DESIGN: Android device support for Orca

> Status: design approved, implementation in progress on `feat/android-device-support`.
> Generated by a multi-agent design workflow (map → design → 3-lens adversarial review → synthesize), grounded against real file paths.

## Summary

Orca today mirrors and drives **iOS simulators** through `EmulatorBridge` (`src/main/emulator/emulator-bridge.ts`), a serve-sim helper, an MJPEG screen stream owned by main, and a normalized tap/gesture RPC contract. This document specifies **Android device support** as a *sibling bridge* (`AndroidBridge`) behind an extracted `MobileDeviceBridge` interface, with a *Strategy* backend layer (`AndroidDeviceBackend`) whose first implementation is **redroid (containerized Android) reached over ADB**, local on Linux or remote over SSH.

The hard technical pivots versus iOS:
- **Codec.** iOS streams MJPEG (one self-contained JPEG per IPC message). Android's source is an **H.264 Annex-B elementary stream**. We keep main owning the socket/tunnel (the load-bearing transport invariant) and do **NAL→access-unit framing in main**, so the renderer keeps the existing *"one IPC message = one independently-decodable unit"* contract and decodes via WebCodecs `VideoDecoder` → `<canvas>`.
- **No KVM.** redroid is a **container on the host kernel** (binder/binderfs + ashmem/memfd, CPU-arch-matched image) — it does **not** use `/dev/kvm`. Availability is gated on the kernel/container capability, not virtualization.
- **One SSH transport model.** For remote hosts, **everything runs remote-side** (`docker`/`adb`/`screenrecord` via `SshConnection.exec`); stdout rides the exec channel back into main. No desktop `adb` dependency, no port-forward in the default path.

This document is the executable spec: it lists every file to add/change, the backend interface, key skeletons, and a 6-phase plan. It folds in the cross-platform/SSH, reuse/naming, and feasibility review critiques as corrections to the design, not addenda.

## Goals and non-goals

### Goals
1. Drive at least one **redroid** Android device from the existing emulator pane: live screen, discrete tap / gesture / text / button / rotate.
2. Run **local on Linux** (host kernel supports binder + matching arch) **and remote over SSH** (Mac/Windows/Linux desktop → a Linux redroid host), reusing Orca's SSH connection machinery.
3. Preserve the **"main owns the socket"** transport invariant and the **codec-agnostic** `emulator:frameStreamFrame` envelope.
4. Make the iOS path **structurally unchanged** behaviorally — only typed against a new interface and given an injected shared registry.
5. Make a **second backend** (`local-adb` + scrcpy) pluggable with **zero `AndroidBridge` change**, proving the Strategy boundary.
6. Stay within lint limits: **300 counted lines for `.ts`, 400 for `.tsx`** (`.oxlintrc.json:69,75`; `skipBlankLines`/`skipComments` true).

### Non-goals
- **WebRTC.** A renderer-side `RTCPeerConnection` would move the media socket out of main and force SDP/ICE brokering through main — directly against the transport invariant and the SSH model. Explicitly rejected; see Stream section.
- **Low-latency / smooth live-drag on Android in Phase 1.** The serve-sim WebSocket HID path stays iOS-only. Android gets discrete RPC tap/gesture; smooth drag returns later via the scrcpy control socket.
- **Hardware-virtualized AVD/QEMU emulators.** Not redroid; out of scope. A KVM gate would only ever belong to such a future backend.
- **Installing `adb` on the user's Mac/Windows desktop.** The remote model runs adb remote-side; no new desktop binary dependency.
- **Multi-host fan-out UI.** We support a configured remote host (referenced by SSH target id), not a host picker, in this iteration.

## Architecture

### Two abstraction layers

**Layer A — sibling bridges behind one interface.** iOS and Android are *sibling bridges*. Extract the method surface the runtime already calls into `interface MobileDeviceBridge` (new `src/main/emulator/mobile-device-bridge.ts`). `EmulatorBridge` gains `implements MobileDeviceBridge` with **no body change** — verified it already exposes `startHelperForDevice`, `tap`, `gesture`, `type`, `button`, `rotate`, `exec` (`emulator-bridge.ts:154–233`) and the runtime calls exactly these (`orca-runtime-emulator.ts:49–105`). This is a typing extraction only, not a behavioral refactor of serve-sim guts.

**Layer B — backend Strategy inside `AndroidBridge`.** redroid-vs-local-adb is a Strategy (`AndroidDeviceBackend`) *inside* `AndroidBridge`. The task's "backend interface" is this one.

```
EmulatorBridge (iOS, serve-sim)  ─┐
                                  ├─ implements MobileDeviceBridge  ← runtime routes by `kind`
AndroidBridge (orchestrator)     ─┘
  ├─ AndroidDeviceBackend (Strategy interface)
  │     ├─ RedroidDockerBackend       (Phase 1 — this doc)
  │     └─ LocalAdbScrcpyBackend       (later — plugs in, no AndroidBridge change)
  ├─ adb-input-control.ts             (tap/swipe/text/keyevent/rotate — backend-agnostic, shared by ALL android backends)
  └─ emulator-session-lifecycle.ts    (SHARED with EmulatorBridge — registry-delegating worktree orchestration)
        └─ uses injected EmulatorSessionRegistry (one instance, both bridges)
```

### Shared session orchestration (reuse correction)

The session/worktree bookkeeping (`registerActiveEmulator`, `getActiveForWorktree`, `getReusableActiveForWorktree`, `stopActiveForWorktree`, `kill`, `shutdown`, `destroyAllSessions`, and the verb preamble `getTargetOrThrow` at `emulator-bridge.ts:131`) are thin shells over the shared registry plus a teardown hook — they are **not** serve-sim guts. Copying them onto `AndroidBridge` would be duplicated orchestration. Instead, extract a composed module:

- **`src/main/emulator/emulator-session-lifecycle.ts`** — registry-delegating orchestration parameterized by a `teardown(session)` hook. iOS passes `stopServeSimForDevice`; Android passes `backend.teardown`. `getTargetOrThrow` lives here and is shared by both bridges. `EmulatorBridge` is refactored to *delegate* to this module (a mechanical extraction of existing shells — serve-sim execution untouched), and `AndroidBridge` reuses it. This keeps both orchestrators thin and under 300 lines.

### Registry as the routing source of truth

The registry (`emulator-session-registry.ts`) already owns `activeByWorktree`/`sessions`. We inject **one** instance into both bridges (change `emulator-bridge.ts:29` from `new EmulatorSessionRegistry()` to a constructor param, default-constructed to preserve existing callers). Each session record gains `kind: 'ios' | 'android'` and `streamKind: 'mjpeg' | 'h264'`, plus a `hostId` so serials are keyed by `(hostId, serial)` — two remote hosts must not collide on `127.0.0.1:5555`.

The runtime routes:
- `attach` / `list` route by an **explicit `--kind`** flag.
- Interaction verbs (`tap`/`type`/`gesture`/`button`/`rotate`) route by the **kind recorded at attach time** in the shared registry.

### Backend interface

Intentionally tiny — the *only* axis on which backends differ is device existence, stream source, and teardown. Input and session bookkeeping live in `AndroidBridge` and are shared.

```ts
// src/main/emulator/android-device-backend.ts
export type AndroidHost =
  | { mode: 'local' }
  // Remote redroid is the Mac/Win/Linux-desktop path. The backend resolves
  // docker/adb/screenrecord remote-side via SshConnection.exec on this target.
  | { mode: 'remote'; sshTargetId: string }   // references an SshConnectionStore target

export type AndroidProvisionTarget = {
  deviceId?: string        // adb serial or orca-generated container id; absent => backend default
  worktreeId?: string
  host: AndroidHost
}

// Opaque handle: main keeps owning the byte source (local child stdout OR remote
// exec-channel stdout). NAL framing happens in main BEFORE these chunks are emitted,
// so each yielded item is one decodable access unit, not a raw socket chunk.
export type AndroidVideoUnit = {
  data: Uint8Array          // one H.264 access unit (Annex-B), key or delta
  key: boolean              // IDR (carries/preceded by SPS+PPS) vs delta
  ptsMicros: number         // synthesized; screenrecord/scrcpy give none
  width: number
  height: number
}

export type AndroidStreamHandle = {
  streamId: string
  streamKind: 'h264'
  units(): AsyncIterable<AndroidVideoUnit>  // forwarded to emulator:frameStreamFrame
  stop(): void
}

export type AndroidBackendAvailability = {
  ok: boolean
  reason?:
    | 'binder_unsupported'      // host kernel lacks binder/binderfs/ashmem
    | 'arch_mismatch'           // image arch != host arch
    | 'docker_missing'
    | 'docker_unprivileged'     // user not in docker group / --privileged disallowed
    | 'ssh_unreachable'
    | 'no_remote_host'          // non-Linux desktop, no SSH target configured
    | 'host_not_linux'
  message: string               // actionable copy for the unavailable pane
}

export interface AndroidDeviceBackend {
  readonly id: 'redroid-docker' | 'local-adb-scrcpy'
  inspect(host: AndroidHost): Promise<AndroidBackendAvailability>
  // Ensure device exists + adb-reachable + getprop sys.boot_completed === 1.
  provision(target: AndroidProvisionTarget): Promise<{ serial: string; host: AndroidHost; hostId: string }>
  startStream(serial: string, host: AndroidHost): Promise<AndroidStreamHandle>
  teardown(serial: string, host: AndroidHost, opts?: { destroy?: boolean }): Promise<void>
}
```

Note the framing decision baked into the interface: `units()` yields **access units with key/delta + synthesized PTS**, computed in main (the stream source does NAL parsing). The renderer must not be handed raw socket chunks.

## Backend #1 — redroid / Docker-over-ADB

### Host resolution (capability-derived, never blind local docker)
`provision` resolves the host before anything:
- `{ mode: 'local' }` is only attempted when `platform() === 'linux'` **and** the binder/arch/docker probe passes. On macOS/Windows, Docker Desktop may be present but **cannot** run a privileged binder-backed redroid container — so local is never attempted on non-Linux. If `platform() !== 'linux'` and no SSH target is configured → return unavailable with actionable copy.
- `{ mode: 'remote'; sshTargetId }` references a stored **`SshConnectionStore`** target (auth/credentials/reconnect already managed), not a free-form host string.

### Availability probe (binder, not KVM)
`android-availability.ts` mirrors `inspectEmulatorAvailability` (`emulator-availability.ts`) in *shape* (runtime capability probe, not a build-time constant) but checks redroid's real requirements:
1. Host is Linux (locally `platform()`; remotely via existing `ssh-remote-platform-detection.ts` / `RemoteHostPlatform` — do not re-`uname` on a fresh channel).
2. **binder available**: `binder_linux` loadable, or `/dev/binderfs` mountable (binderfs is also required for >1 concurrent container).
3. **CPU arch matches** the redroid image (this host is `aarch64` → arm64 image; an x86_64 image would fail).
4. `docker` reachable and the SSH user can run privileged containers (in `docker` group / rootless).
5. Best signal: a **canary `docker run`** that reaches `sys.boot_completed === 1`.

The error code is **`emulator_android_kernel_unsupported`** (not `emulator_kvm_unavailable`). KVM is never referenced.

### Launch / attach
`RedroidDockerBackend.provision(target)`:
- Idempotent ensure: `docker ps --filter label=orca.session=<id>`; if absent, `docker run -d --privileged --label orca.session=<id> --label orca.host=<hostId> --name orca-redroid-<id> redroid/redroid:<androidVer>-<arch> androidboot.hardware=redroid ...` with a **distinct binder context per container** (binderfs) from `redroid-container-spec.ts`.
- Boot wait: `adb connect <serial>` then poll `adb -s <serial> shell getprop sys.boot_completed` until `1` (30–60s cold-boot timeout) — the Android analogue of `waitForServeSimEndpointReady`.
- Returns `{ serial: '127.0.0.1:5555' /* on the host where adb runs */, host, hostId }`.

### Orphan reaping
redroid containers survive an Orca crash and hold binder contexts. Mirror the existing terminal-orphan-cleanup pattern: on startup, sweep `docker ps --filter label=orca.host=<hostId>` (locally and per active SSH host) and reap stale containers whose session ids are not live. Surface `docker_unprivileged` distinctly when `--privileged` is disallowed.

### Taps / gestures (shared, backend-agnostic)
`adb-input-control.ts` maps the existing 0..1-normalized RPC contract onto device pixels using the live stream size **and current rotation**:
- tap → `input tap <px> <py>`
- gesture polyline → segmented `input swipe x1 y1 x2 y2 <ms>` — **kept discrete / low-segment**: each `input` invocation spawns `app_process` (~100–300ms), so a many-segment polyline janks. We do not promise smooth drag on the adb path.
- `type` → `input text` (escape spaces as `%s`; no emoji)
- `button` → `input keyevent <KEYCODE>`
- `rotate` → `settings put system user_rotation` — note this changes stream dimensions and **requires a decoder re-init** (see Stream section).

This is in `AndroidBridge`, not the backend — input is identical across all Android backends. The `sendTouch` seam stays the abstraction boundary so the scrcpy control socket can replace it later with zero call-site change.

## Stream and input handling — the MJPEG vs H.264 gap, explicitly

### What MJPEG does today (grounded)
`MjpegFrameStream` (`src/main/emulator/mjpeg-frame-stream.ts`) **parses JPEG frame boundaries in main** (`extractJpegFrames`) and emits one `emulator:frameStreamFrame` per **complete JPEG**. The renderer (`use-emulator-frame-stream.ts:72–86`) treats each message as a self-contained image: `URL.createObjectURL(new Blob([bytes], {type:'image/jpeg'}))` → `<img>.src`. The transport is byte-agnostic, but the **per-message contract is "one whole, independently-displayable frame."**

### Why not WebRTC (the gap, named)
WebRTC would put the `RTCPeerConnection` and the media socket **in the renderer**, forcing SDP/ICE brokering through main and breaking *"main owns the socket."* Over SSH this is fatal: main holds the tunnel. WebRTC is rejected. The real Android source is **raw H.264** (`screenrecord`/scrcpy), not a WebRTC track — so the honest comparison is **MJPEG vs raw H.264 Annex-B**.

### The actual gap: H.264 is not frame-aligned to socket chunks
Raw `screenrecord --output-format=h264 -` is an **Annex-B elementary stream**: no container, no timestamps, NAL boundaries unaligned to socket reads. Naively "forwarding NAL chunks" would **break the one-message-one-frame contract** the renderer depends on. So the framing work MJPEG does in main must be **reproduced in main for H.264**:

**Produce (main) — `android-stream-source.ts`:**
- Spawn the source: Phase 1 `adb -s <serial> exec-out screenrecord --output-format=h264 --time-limit 180 -` (no scrcpy binary, no extra dep). Remote: the same command via `SshConnection.exec`, stdout streaming back through the exec channel.
- **Parse the byte stream into NAL units → access units** (start-code scan, AUD/SPS/PPS/IDR detection), classify **key vs delta**, extract `width/height` from SPS, and **synthesize PTS** (monotonic, derived from a fixed cadence since screenrecord emits none).
- **Own restart**: `screenrecord` has a hard **180s cap**, so the child *will* exit every 3 minutes; the source restarts it, prepends the fresh SPS/PPS+IDR, and emits a keyframe so the decoder re-syncs. Over SSH, exec channels do **not** survive relay-lost/reconnect — the source re-establishes the exec channel on SSH reconnect events and restarts the child.
- On **rotation/resolution change**, dimensions are baked at stream start, so the source tears down and restarts, emitting a new SPS/PPS+IDR; the renderer re-inits the decoder.

**Transport (reused, unchanged):** `emulator:frameStreamFrame` already ships raw `ArrayBuffer` and is codec-agnostic. Each message now carries **one access unit** plus the small metadata the renderer needs (`key`, `ptsMicros`, `width`, `height`) — preserving the "one message = one decodable unit" invariant. Main owns the socket/tunnel throughout.

**Consume (renderer) — `use-emulator-video-stream.ts`:**
- **Runtime per-session gate**: `await VideoDecoder.isConfigSupported({ codec: 'avc1.42E01E' /* or SPS-derived */ })`. If unsupported on this Electron/OS/hardware, fall to the ffmpeg-transcode fallback.
- Configure `VideoDecoder` with an **Annex-B-compatible** config (no `description`/avcC; or extract SPS/PPS into avcC) — feed `EncodedVideoChunk({ type: key?'key':'delta', timestamp: ptsMicros, data })`, paint frames to `<canvas>`. `videoWidth/videoHeight` supply the `onStreamSize` that `<img>.naturalWidth` gave before.

**ffmpeg fallback (named, honest):** transcode H.264→MJPEG **in main** so the renderer surface is unchanged. This is a **correctness** fallback, not a performance-equivalent one: over SSH it re-inflates bandwidth and adds main-process CPU + latency. Used only when WebCodecs `avc1` is unsupported.

### IPC ownership: main-spawned source vs renderer-pull-by-URL
The existing `emulator:frameStreamStart` is **renderer-initiated and URL-addressed** — the handler does `new MjpegFrameStream(streamUrl)` and opens the HTTP socket itself. The H.264 source is a **main-spawned child/exec channel** that `AndroidBridge` already owns from provisioning. We bridge the two registries:
- Add a **main-side stream-handle registry**. `frameStreamStart` with `streamKind:'h264'` **looks up an existing `AndroidStreamHandle`** by `streamId` instead of opening a URL.
- Define lifecycle: who kills the source child on renderer teardown vs session teardown (the handle registry owns this; session teardown wins).

### FrameStream contract (reuse correction)
Define one `FrameStream` interface (`start(): void; stop(): void`) in the emulator/ipc module; both `MjpegFrameStream` and the new `H264FrameStream` `implements` it; type the IPC session's `stream` field and the factory return against it — retiring the ad-hoc structural `{start;stop}` and the "parallel mirrored class" duplication.

### Input asymmetry (the degradation story)
The iOS **live-drag WebSocket HID path** (`use-emulator-control-stream.ts`, serve-sim wire format via `encodeServeSimTouchFrame`) is **iOS-only** and gated off for Android. Android reuses the 0..1 **RPC** tap/gesture path fully. This asymmetry *is* the graceful degradation; smooth drag returns when `LocalAdbScrcpyBackend` brings the scrcpy control socket behind the unchanged `sendTouch` seam.

## Cross-platform and SSH behavior

### Single SSH transport model: everything runs remote
For `{ mode: 'remote' }`, **`docker` / `adb` / `screenrecord` all run remote-side** via:

- **`SshConnection.exec(cmd, options): Promise<ClientChannel>`** (`src/main/ssh/ssh-connection.ts:94`) — a streaming channel, used for both one-shot `docker`/`adb` calls and the long-lived `screenrecord` stdout. **Not** `SshChannelMultiplexer` (`src/main/ssh/ssh-channel-multiplexer.ts`), which is a **JSON-RPC relay** (`request(method, params)` at line 153) and cannot exec shell commands. The handlers/manager live behind `registerSshHandlers()` (`src/main/ipc/ssh.ts:562`).
- Connections are obtained from the existing **`SshConnectionStore` / `SshConnectionManager`** (`ssh-connection-manager.ts`) by `sshTargetId`, reusing auth/credentials/reconnect.

Consequences: **no `adb` binary on the desktop**, serial is `127.0.0.1:5555` **on the remote host**, and `SshPortForwardManager.addForward` (`ssh-port-forward.ts`) is **not** in the default path.

### Remote command building
`adb-command-execution.ts` must **resolve binaries via PATH** (`execa`; Windows `adb.exe`), never hardcode `/usr/bin/adb` or POSIX paths. For the remote side it must reuse the **`RemoteHostPlatform`-aware builders / `shellEscape` in `ssh-remote-commands.ts`** (the remote shell may not be bash) rather than hand-joining args. If this file approaches 300 counted lines, split SSH-wrapping into a sibling before it lands.

### Watcher scoped to the connection, not process-global
`adb track-devices` is a long-lived adb-server connection. For a remote host it runs **remote-side** and is **scoped to the SSH connection lifecycle** — created on connect, torn down on disconnect, re-established on reconnect — not started once at app boot beside the local-only `serveSimStateWatcher`. One watcher per active Android host, feeding the **same `registerActiveEmulator` sink** for auto-attach parity.

### Availability / degradation matrix
| Situation | Result |
|---|---|
| Linux + binder + matching arch + docker | local redroid available |
| macOS/Windows + configured SSH target reaching a valid Linux host | remote redroid available |
| macOS/Windows + no SSH target | `no_remote_host` — actionable copy, never attempt local docker |
| Linux, KVM present but no binder | `binder_unsupported` (the old KVM probe would falsely pass here) |
| arch mismatch (e.g. x86_64 image on aarch64) | `arch_mismatch` |
| docker present, user lacks privilege / `--privileged` disallowed | `docker_unprivileged` |
| container unreachable | `emulator_redroid_unreachable` with remediation hint |
| Android session active | live-drag WebSocket disabled (iOS-only); discrete tap/gesture works |

Availability is a **runtime** capability probe and the unavailable pane shows capability-based copy (parallel to iOS "requires a Mac").

## Phased implementation plan

**Phase 1 — scaffold (no behavior).** Add `mobile-device-bridge.ts`, `frame-stream-contract.ts`. Extract `emulator-session-lifecycle.ts` from `emulator-bridge.ts` (incl. `getTargetOrThrow`); make `EmulatorBridge implements MobileDeviceBridge`, inject shared registry. Add `kind`/`streamKind`/`hostId` to session structs, types, error codes (binder-based, **no KVM code**). Hoist `EMULATOR_TARGET_FLAGS`; thread `--kind` through CLI selectors/specs and `attach`/`list` RPC params. Stub `AndroidBridge` + `AndroidDeviceBackend` + `RedroidDockerBackend` (methods throw). Construct disabled in `index.ts`. **Exit:** typechecks, iOS behaviorally unchanged, existing tests green, `orca emulator list --kind android` returns "unavailable".

**Phase 2 — discovery + availability.** Implement `adb-command-execution.ts` (local `execa` + remote `SshConnection.exec` via `ssh-remote-commands.ts`), `adb-android-devices.ts`, `android-availability.ts` (binder/binderfs + arch via `ssh-remote-platform-detection.ts` + docker + canary). Wire `getAndroidBridge`/`resolveBridge` in the runtime host; Settings pane reads `androidRedroidSshTargetId`. **Exit:** availability correctly reports local-binder vs remote-SSH vs none; `emulator list --kind android` enumerates real devices.

**Phase 3 — provision + input.** `redroid-container-spec.ts` (arch-matched image, binderfs context) + `RedroidDockerBackend.provision/teardown` + **orphan-reap sweep**; `adb-input-control.ts`. **Exit:** `attach --kind android` boots/attaches a container locally; tap/type/button/discrete-gesture/rotate hit the device; `--privileged`/docker-group failures surface distinctly.

**Phase 4 — stream end to end (local).** `android-stream-source.ts` (screenrecord-H264 **with NAL framing + PTS synth + 180s restart**), `h264-frame-stream.ts` + factory + main-side handle registry, renderer `use-emulator-video-stream.ts` (**runtime `isConfigSupported` gate**, Annex-B config) + `<canvas>` surface, `emulator-pointer-transport.ts` extraction, capability-based unavailable copy. Fall to ffmpeg-transcode if WebCodecs `avc1` unsupported. **Exit:** live Android screen in the pane on local Linux; rotation re-inits cleanly; decoder survives the 3-minute restart with only a brief stutter.

**Phase 5 — remote SSH + auto-attach.** Route all `docker`/`adb`/`screenrecord` remote-side via `SshConnection.exec`; stream stdout rides the exec channel; reconnect re-establishes child + channel. `android-track-devices-watcher.ts` scoped to the SSH connection lifecycle, feeding `registerActiveEmulator`. **Exit:** a Mac/Windows user drives a remote-Linux redroid over SSH with no desktop adb; auto-attach parity with serve-sim; reconnect resumes the stream.

**Phase N — backend #2 (scrcpy).** `LocalAdbScrcpyBackend implements AndroidDeviceBackend` — scrcpy's own H.264 socket (no 180s cap, keyframe-on-request, resize events) + control socket. Re-enable smooth live-drag for Android behind the unchanged `sendTouch` seam. **Zero `AndroidBridge` change.**

## Open risks

1. **redroid host kernel (highest).** binder/binderfs + ashmem/memfd, not KVM; >1 concurrent container needs **binderfs** + per-container binder context. Stock distro kernels often lack binder. *Mitigation:* canary-boot probe in availability; require binderfs for multi-worktree; clear `binder_unsupported`/`arch_mismatch` copy.
2. **CPU-arch image matching.** redroid images are arch-specific. *Mitigation:* probe `RemoteHostPlatform` arch, select image suffix, fail with `arch_mismatch`.
3. **screenrecord is demo-grade.** 180s cap → periodic re-key stutter; recorder-buffered latency; rotation/resolution change breaks the stream; default swiftshader gives low fps. *Mitigation:* restart/re-key logic + decoder re-init; treat as stop-gap and pull scrcpy forward.
4. **Renderer H.264 decode portability.** WebCodecs `avc1` and Annex-B vs avcC handling vary by Electron/OS/hardware. *Mitigation:* per-session runtime `isConfigSupported`; ffmpeg-transcode fallback (correctness, not performance).
5. **SSH durability.** Exec channels are not restored by `restorePortForwards`; relay-lost drops them. *Mitigation:* stream source owns child-exit + reconnect restart; watcher scoped to connection lifecycle.
6. **Orphan containers / privilege.** Crash leaves remote redroid running. *Mitigation:* label + startup sweep + TTL/heartbeat; surface `docker_unprivileged`.
7. **adb input cost.** Each `input` spawns `app_process`; multi-segment swipes jank. *Mitigation:* discrete/low-segment gestures; defer smooth drag to scrcpy.
8. **Serial namespace collisions.** `127.0.0.1:5555` repeats across hosts. *Mitigation:* key registry + sessions by `(hostId, serial)`.
9. **`emulator-device-frame.tsx` line cap.** Already 410 (over 400). *Mitigation:* the `emulator-pointer-transport.ts` extraction is mandatory.
10. **`adb-command-execution.ts` size.** Risks >300 counted. *Mitigation:* split SSH-wrapping into a sibling.
